# Storage, schema and migrations

Darwin does not know where things are stored. The core (`[darwin]`) ships domain, services,
tokens, transports and plugins, and **no** backend. You pick one:

```sh
pip install 'hexcore[darwin-sqlalchemy]'   # PostgreSQL, SQLite, MySQL
pip install 'hexcore[darwin-beanie]'       # MongoDB
```

They are separate rather than one extra with both because a deployment picks **one**: whoever
picks Mongo has no reason to install SQLAlchemy, Alembic and asyncpg — that is ~15 MB and a
supply-chain surface they do not use.

---

## How the backend is chosen

```python
IdentityConfig(storage="sqlalchemy")   # explicit
IdentityConfig(storage="beanie")
IdentityConfig()                       # detected
```

When it is `None` it is detected from what is installed, with a rule worth knowing before it
surprises you: **if both are installed, it refuses**.

```
Hay más de un backend de almacenamiento instalado (beanie, sqlalchemy) y Darwin no
elige por vos: el que quede afuera se nota recién cuando la app arranca contra una
base vacía.

Declaralo:

    IdentityConfig(storage="sqlalchemy", ...)
```

Guessing by an implicit rule would make the backend depend on what else happens to be installed,
and the symptom — an app that starts against an empty database — appears far from the cause.

If neither is installed, the error names both commands.

---

## The neutral-name contract

The core never names a backend. Each backend exposes the **same names**:

| Name | What it is |
| :-- | :-- |
| `UserRepository` | Users |
| `SessionRepository` | Sessions |
| `AccountRepository` | Linked accounts |
| `VerificationRepository` | Single-use tokens |

And for plugin schemas:

| Constant | Where | What it collects |
| :-- | :-- | :-- |
| `PLUGIN_MODELS` | `orms/sqlalchemy/models.py` | The plugin's SQL models |
| `PLUGIN_DOCUMENTS` | `orms/beanie/repository.py` | The Beanie documents |

It is the same mechanism for both, and for the same reason: whoever collects them cannot know each
plugin's own names in advance.

The boundary is not a convention. There are tests that run in subprocesses with a finder in
`sys.meta_path` that **blocks** packages: the core imports with all six plugins blocked, and each
plugin imports with the other five blocked.

## SQL: Alembic, and the failure mode that raises nothing

> **If you use SQL, this is the most important section of the module.**

A table that exists in the database and is **missing from `Base.metadata`** makes the next
`alembic revision --autogenerate` emit an `op.drop_table` for it. With data in it. It is Darwin's
worst failure mode because it is the only one that does not fail: the migration is generated
cleanly and the damage appears when it is applied.

To prevent it, Alembic's `env.py` has to load the identity schema:

```python
# env.py — the relevant fragment
from hexcore.darwin import ensure_identity_schema_loaded

DARWIN_PLUGINS: list[str] = ["two_factor", "passkey"]   # the ones you use
ensure_identity_schema_loaded(plugins=DARWIN_PLUGINS)
```

The `env.py` generated by `hexcore` already carries that call with an empty list and the comment
explaining what happens when one is missing.

### Why the list is passed by hand

Because discovering the plugins automatically would be **worse**. The six plugins Darwin ships live
in the same distribution, so they are all on disk whether you installed the extra or not:
discovering by presence would create a `darwin_passkey` table for someone who never used passkeys.

The only honest source of "which plugins does this deployment use" is the list you pass to
`configure_identity`. In `env.py` there is no container yet, so there the list has to be repeated.

### The safety net

Repeating a list is a source of omissions, so the fix does not end there. At startup there *is* a
container, and there the list is exact: `IdentityStep` compares `Base.metadata` against the core
plus the active plugins, and if anything is missing it logs an error naming **the missing tables
and the exact list to copy into `env.py`**.

That is the division of labor: the `env.py` function cannot guess, so it asks; the startup step
does not need to guess, so it verifies. Discovering a table was missing by reviewing a migration
diff is too late to rely on someone reviewing it.

### Creating and dropping without Alembic

For tests or scripts:

```python
from hexcore.darwin import create_identity_tables, drop_identity_tables

await create_identity_tables(engine, plugins=["two_factor"])
await drop_identity_tables(engine, plugins=["two_factor"])
```

Order matters and is already handled: `identity_tables` puts the core's first and the plugins'
last, and `drop` reverses the whole list, so the plugin tables are dropped first — the only order
that works, because they reference `darwin_user`.

## Mongo: the same hole, a different symptom

```python
from hexcore.darwin.infrastructure.orms.beanie.schema import init_identity_documents

await init_identity_documents(db, plugins=["two_factor", "passkey"])
```

Here it is not a lost migration: a `Document` that `init_beanie` never saw **does not work**, so
omitting an active plugin leaves it failing on the first query with `CollectionWasNotInitialized`.

The plugins go in **that same call**, not in one of their own. `init_beanie` does not accumulate:
a second call against the same database replaces the first call's registry, so initializing the
core and then each plugin would leave only the last one working. That is why `plugins=` is a
parameter and not a separate function.

If your application has its own documents, use `identity_documents()` to get the list and combine
it with yours in a single `init_beanie` call:

```python
from beanie import init_beanie
from hexcore.darwin.infrastructure.orms.beanie.schema import identity_documents

await init_beanie(
    database=db,
    document_models=[*identity_documents(plugins=["two_factor"]), MyDocument, OtherDocument],
)
```

Or declaratively, with `hx.BeanieStep(documents=[...])` in the lifespan, passing it the complete
list.

## Core tables

| Table | What it holds |
| :-- | :-- |
| `darwin_user` | Users |
| `darwin_session` | Sessions — with `actor_user_id` **and** `subject_user_id` |
| `darwin_account` | Linked accounts (OAuth, credentials) |
| `darwin_verification` | Single-use tokens |
| `darwin_audit_log` | Audit trail |
| `darwin_jwks` | Signing keys |

The session persists **two** principals rather than a single `user_id`. That is what makes
impersonation auditable, and the decision belongs to the original schema design and not to the
plugin that uses it: an impersonated context without both cannot be built.

## Your own user model

The models are **mixins**, not mapped classes, so you can compose them with your `Base` and rename
tables:

```python
from hexcore.darwin import UserMixin
from hexcore.sql import Base


class User(UserMixin, Base):
    __tablename__ = "users"
    # your columns
```

And declare it:

```python
IdentityConfig(user_model=User)
```

It is validated **at configure time**, not on the first login: it rejects a `BaseModel[T]` — which
would blow up after the commit — and a class that does not compose `UserMixin`.

`validate_user_model(model_cls)` is the check, and `IdentityStep` runs it at startup.

The available mixins are `UserMixin`, `SessionMixin`, `AccountMixin`, `VerificationMixin`,
`AuditLogMixin`, `JwksMixin` and `TimestampMixin`, with the default table names exposed as
`DEFAULT_USER_TABLE`, `DEFAULT_SESSION_TABLE`, `DEFAULT_ACCOUNT_TABLE` and
`DEFAULT_VERIFICATION_TABLE`.

## Ports

The ports live in `hexcore.darwin.domain.ports` and define the contracts backends implement:

| Port | What it covers |
| :-- | :-- |
| `AbstractUserRepository` | User CRUD, lookup by email, generation counter |
| `AbstractSessionRepository` | Session CRUD, lookup by token, reuse detection, the reaper |
| `AbstractAccountRepository` | External provider accounts (OAuth, passkeys) |
| `AbstractVerificationRepository` | Single-use tokens (email verification, magic links, 2FA challenges) |
| `AbstractRevocationList` | The cached `sid` denylist for immediate revocation |
| `AbstractAuditSink` | The audit trail, optional |
| `AbstractClock` | Injectable clock (production: `SystemClock`; tests: `FixedClock`) |
| `AbstractPasswordHasher` | Password hashing (production: `Argon2PasswordHasher`) |

Plugins resolve their backend by asking **the container**, not by detecting on their own. If each
detected independently, a deployment with both extras could end up with the core on one backend
and a plugin on the other — and the symptom is that login works and the second factor finds
nothing. `plugin_storage_backend()` and `plugin_repositories(plugin)` in
`hexcore.darwin.plugins.storage` implement that resolution.

---

## Known limitation

On Mongo, the audit trail is not transactional with the operation it audits. On SQL both go in the
same transaction; on Mongo that would require a multi-document transaction, which requires a
replica set. If your deployment has one, you can inject your own `AbstractAuditSink` that uses it.
