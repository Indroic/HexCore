# CLI

The package installs a `hexcore` executable (and generated projects ship an equivalent
`manage.py`). It is written with Typer, so `hexcore --help` and `hexcore <command> --help` work at
every level.

```sh
hexcore --help
```

---

## `hexcore init` — create a project

```sh
hexcore init my_project --template hexagonal
hexcore init my_project -t vertical-slice
```

It fails if the folder already exists, and if the template is not one of the two.

### The `hexagonal` template

Layers first, the domain inside:

```
my_project/
├─ src/
│  ├─ domain/
│  ├─ application/
│  └─ infrastructure/
│     └─ database/
│        ├─ models/          # SQLAlchemy
│        ├─ documents/       # Beanie
│        └─ migrations/versions/
├─ tests/domain/
├─ alembic/env.py
├─ alembic.ini
├─ config.py
└─ manage.py
```

`repository_discovery_paths` is seeded with `src.infrastructure.repositories` and
`src.infrastructure.repositories.implementations`.

### The `vertical-slice` template

The feature first, the layers inside each one:

```
my_project/
├─ src/
│  ├─ features/
│  └─ shared/
│     ├─ domain/
│     ├─ application/
│     └─ infrastructure/
│        └─ database/{models,documents,migrations}
├─ tests/features/
├─ config.py
└─ manage.py
```

`repository_discovery_paths` is seeded with `src.features` and
`src.shared.infrastructure.repositories`.

### What both do

1. Create the packages with their `__init__.py` files.
2. Write `README.md`, `.gitignore` and `manage.py`.
3. Write `config.py` at the root **if it does not exist** — an existing `config.py` is preserved.
4. Run `alembic init`, point `version_locations` at the template's migrations directory, set
   `target_metadata = Base.metadata`, and wire up `env.py` (see below).
5. Run `ruff format` over what was generated, if `ruff` is installed. It is not a requirement: it
   stopped being a runtime dependency precisely because it was imposed on everybody for a command
   you run once.

### The generated `env.py`

This is the part most worth looking at, because it contains the three lines that prevent data
loss:

```python
ensure_framework_models_loaded()      # the framework's tables (hexcore_cron_jobs)

DARWIN_PLUGINS: list[str] = []        # ← fill this in with the plugins you use
ensure_identity_schema_loaded(plugins=DARWIN_PLUGINS)

import_all_models(models)             # yours, recursively
```

⚠️ A table that exists in the database and is **missing from `Base.metadata`** gets an
`op.drop_table` in the next autogenerated migration. With data in it. It is the framework's worst
failure mode because it does not fail: the migration is generated cleanly and the damage appears
when it is applied.

The Darwin block is wrapped in a `try/except ImportError`, so a project without the `[darwin]`
extra is not broken by it.

## `hexcore create-domain-module` — a domain module

```sh
hexcore create-domain-module sales
```

Creates, under the project's domain directory:

```
sales/
├─ __init__.py
├─ entities.py
├─ repositories.py      # I<Entity>Repository, deriving from IBaseRepository
├─ services.py
├─ value_objects.py
├─ events.py
├─ enums.py
└─ exceptions.py
```

Plus the matching test module. The name must be a valid Python identifier; if the module already
exists, it is not overwritten.

## Migrations

```sh
hexcore make-migrations "add the tickets table"   # alembic revision --autogenerate -m "..."
hexcore migrate                                   # alembic upgrade head
```

These are thin wrappers over Alembic: they run in the current directory and use your
`alembic.ini`. The URL comes from `config.sql_database_url` — the **synchronous** DSN — which is
what the generated `env.py` injects with `config.set_main_option`.

---

## `hexcore test`

```sh
hexcore test
hexcore test src/domain --extra-args "-k users -q"
```

A wrapper over `pytest`. The first argument is the path (default: `test`), and `--extra-args` is
passed through verbatim. It propagates the exit code, so it works in CI.

## `hexcore identity` — Darwin's commands

The identity sub-app. At its top level it imports only `typer` and stdlib, so it shows up in
`--help` even without the extra installed, and each command imports what it needs when it runs.

### `generate-secret`

```sh
export HEXCORE_DARWIN_SECRET_KEY="$(hexcore identity generate-secret)"
```

Emits a `secrets.token_urlsafe(48)`. It exists because the secret **deliberately has no
default**, and the first obstacle for anyone wiring up Darwin is having to look up how to generate
one. A command solves that before anybody is tempted to type `"changeme"`.

### `generate-keys`

```sh
hexcore identity generate-keys --algorithm Ed25519 --kid 2026-01
```

Emits the token signing key pair as JWK, on stdout, ready to redirect into a secret manager:

```json
{
  "kid": "2026-01",
  "algorithm": "Ed25519",
  "status": "active",
  "public_jwk": { "...": "..." },
  "private_jwk": { "...": "..." }
}
```

⚠️ **The private key comes out in the clear.** Do not leave it in your shell history or in a file
in the repository. The warning goes to **stderr** precisely so it does not pollute what you
redirect.

Both JWKs are emitted **parsed**, not as the string `SigningKey` stores: a secret manager
receiving JSON with a JSON string inside forces a double parse on the other side, and that is the
step somebody ends up working around by pasting the private key into an intermediate file.

### `create-tables`

```sh
hexcore identity create-tables
```

Creates the identity tables against `config.async_sql_database_url`. **This is a shortcut for
development and tests.** In production use Alembic: the function is idempotent but versions
nothing, so a later schema change has nowhere to migrate from.

### `check-schema`

```sh
hexcore identity check-schema
```

Verifies that the identity tables are in `Base.metadata` and **exits with code 1** if any are
missing, so you can put it in a pre-commit hook or in CI:

```
Faltan en Base.metadata: darwin_session, darwin_verification.

`alembic revision --autogenerate` les va a emitir op.drop_table. Importalas desde tu
paquete models/, o agregá `ensure_identity_schema_loaded()` al env.py.
```

It is the check that prevents the module's most expensive data loss: with Darwin, the table that
gets dropped is the entire credential store.

### `plugins`

```sh
hexcore identity plugins myapp.identity
```

Reads a module exposing a `plugins: PluginRegistry` or a `PLUGINS: list[DarwinPlugin]`, and lists
what each plugin contributes: routes, commands, hooks and tables. It is useful for two things —
seeing at a glance the surface you are mounting, and getting the exact list that belongs in the
`DARWIN_PLUGINS` of your `env.py`.

## `manage.py`

`hexcore init` leaves this at the project root:

```python
from hexcore.infrastructure.cli import app as CLI

if __name__ == "__main__":
    CLI()
```

It is the same CLI, invoked from the project: `python manage.py migrate` is equivalent to
`hexcore migrate`, with the advantage that it runs with the project environment's interpreter
without depending on the executable being on `PATH`.
