# Contribution guidelines

Thanks for your interest in contributing to HexCore. To keep collaboration organized and
efficient, please follow these guidelines.

## 1. Code of conduct

Always keep communication respectful and professional. Read the
[Code of Conduct](CODE_OF_CONDUCT.md) before interacting.

## 2. How to contribute

- **Fork** the repository and create a branch for your contribution (`feat/name`, `fix/name`,
  etc.).
- Make your changes on that branch and make sure the code works.
- Write a clear, detailed description in your pull request.
- Link the relevant issues in your PR where applicable.

## 3. Code style and formatting

- Follow the Python style guide ([PEP8](https://pep8.org/)).
- Use comments where they clarify the *why* of the code, not the *what*.
- Include unit tests for new features and fixes. Every fix lands with at least one test that
  fails before and passes after.

```sh
uv sync --extra all --group dev
uv run python -m pytest -q
uv run pyright hexcore
```

CI fails if any test is **skipped**: a skip means an extra is missing from the environment, and
reporting green without having run half the suite is worse than failing.

## 4. `CHANGELOG.md` is never touched in a PR

**Rule: no PR edits `CHANGELOG.md`.** It is generated by `commitizen` at release time from the
conventional commits. If a change deserves prose, that prose goes in the **commit body**, not
in the changelog.

This is not a style preference. A changelog is written by *prepending*, so every branch and
every `cz bump` on master edits **the same line 1**: with N open branches, each release breaks
all N. In the previous round of improvements this cost three rounds of conflicts, and the cost
went up every time — the first was deleting three markers, the third required relocating blocks
between sections.

Since the commits are already conventional and `commitizen` is already configured
(`[tool.commitizen]` in `pyproject.toml`), the changelog writes itself:

```sh
cz bump            # computes the version, tags, and regenerates the CHANGELOG
```

**This repo has two independent release pipelines, one per package** — CI runs both on
every push to `master` (`bump_ver.yml`, jobs `bump-version` and
`bump-version-darwin-client`), and neither is triggered by hand:

| | `packages/hexcore/` | `packages/darwin-client/` |
|---|---|---|
| Tag format | `hexcore-v$version` | `darwin-client-v$version` |
| Config | `packages/hexcore/pyproject.toml` `[tool.commitizen]` | `packages/darwin-client/.cz.toml` |
| Changelog | `CHANGELOG.md` (repo root) | `packages/darwin-client/CHANGELOG.md` |
| Publishes to | PyPI, via `publish-to-pypi.yml` | npm, via `publish-darwin-client-to-npm.yml` |

**`@hexcore-js/darwin-client@0.1.0` was published by hand**, before
`publish-darwin-client-to-npm.yml` existed (npm's trusted publishing requires the package to
already exist before you can configure it). The `darwin-client-v0.1.0` tag came afterwards,
only as an anchor for `cz bump` to start counting from — it did not trigger a real publish:
the workflow checks the version against the registry first and no-ops if it's already there.
From `v0.2.0` onward, everything (tag, changelog, and publish) comes out of the automation.

**Each bump only fires when its own package changed.** `bump_ver.yml` opens with a `changes`
job that diffs the push and decides, per package, whether its bump job runs at all:

| Bump | Fires when the push touches |
| :-- | :-- |
| `bump-version` (Python) | `packages/hexcore/`, `docs/hexcore/`, `uv.lock`, root `pyproject.toml` |
| `bump-version-darwin-client` | `packages/darwin-client/`, `docs/darwin-client/`, root `package.json`, `package-lock.json` |

If the diff base is unusable (a force-push, a truncated history), both run: publishing one
version too many is recoverable with a yank, and publishing none leaves a written fix that
never reaches anybody.

⚠️ **This scopes when a bump *fires*, not how `cz` *counts*.** Neither `cz` config filters
commits by the path they touched, so a `feat:` that only touched one package still counts
toward the other package's version the next time that one does bump. Path-filtering the trigger
defers the spurious bump; it does not eliminate it. Eliminating it would need a fork of
commitizen's changelog generation, which is not worth the cost — most `feat:`/`fix:` work
already carries a scope like `(darwin)`/`(darwin-client)` in its subject, so the changelog reads
correctly even when the version number moved for a neighbour's commit.

The test workflows are scoped the same way, and for the same reason — `pytest.yml` and
`typing.yml` skip when nothing Python changed, `node.yml` skips when nothing in the client
changed. In all four cases the filter is a `changes` **job**, never a `paths:` on the `on:`
block: a workflow that `paths:` filters out never starts, so it never publishes a check, and a
required check that never reports leaves the pull request blocked on
*"Expected — Waiting for status"* forever. A job skipped by an `if:` does report, as `skipped`,
which branch protection counts as success. **The required checks are the fixed-name aggregators**
— `python-ok`, `typing-ok`, `node-ok` — and never the jobs they gate.

What is asked in return: **write the commit so it reads well in the changelog**. The subject is
the line that will be published; the body explains the *why*, which is what a `git log` cannot
reconstruct afterwards.

### Bringing a diverged branch up to date: `merge`, not `rebase`

```sh
git config rerere.enabled true     # once, before you start
git merge origin/master
```

With `rebase`, a conflict repeats once for every commit that touched the file. With `rerere`
enabled, one resolution replays itself across the rest of the branches in the stack.

### "I can't merge" is almost never a conflict

`mergeable: MERGEABLE` only says there are no conflicts; what blocks the button is
`mergeStateStatus`. Diagnose before touching git:

```sh
gh pr view <n> --json mergeable,mergeStateStatus,reviewDecision
gh pr checks <n>
```

`DIRTY` = real conflicts · `UNSTABLE` = checks pending or failing · `BEHIND` = the base requires
being up to date · `BLOCKED` = missing review · `CLEAN` = ready.

## 5. Documentation

All documentation for the monorepo lives in [`docs/`](./docs/) — both packages, in two
languages:

```
docs/
├── README.md                  ← index: both packages, both languages
├── ARCHITECTURE_TYPING.md     ← the Python package's strict-typing contract
├── hexcore/{en,es}/           ← the Python meta-framework, Darwin included
└── darwin-client/{en,es}/     ← the agnostic TypeScript client
```

**English is the reference version** — it is written there first — and `es/` is its
translation. If the two ever contradict each other, English wins.

The package `README.md` files stay complete and self-sufficient, because they are what PyPI and
npm render. They link into `docs/` with **absolute GitHub URLs**: a relative link does not
resolve on a package registry page, so a relative one there is a broken link for everybody who
did not clone the repo.

**If a document shows code, there is a test that runs it.**
`packages/hexcore/tests/test_documentation_examples.py` walks `docs/hexcore/**/*.md` and
verifies that every `from hexcore… import …` resolves against the real API and that every facade
attribute is in its `__all__`. The walk is automatic, so a new guide enters the gate without
being added to any list. `docs/darwin-client/` is outside that walk: its code blocks are
TypeScript and have no `from hexcore…` to resolve.

A documentation change that only touches one language leaves the other one lying. If you change
a guide, change both — or say so in the PR so somebody else can.

## 6. Pull request review

- Every PR is reviewed before being accepted. Changes or clarifications may be requested.
- Reply to reviewer comments to keep the process moving.
- Describe the problem, the reproduction, the solution, and **why that option** over the
  alternatives.

## 7. Issues

- Describe clearly the problem you hit.
- Provide the relevant information: logs, versions, steps to reproduce.

## 8. Communication

- Use issues and discussions for questions, suggestions or proposals.
- If you are unsure how to start, open an issue asking for direction.

## 9. Publishing a major

`commitizen` computes the version from the commits: a `BREAKING CHANGE:` in the body, or a `!`
in the subject, triggers a major. Before merging to `master` with a breaking change pending:

1. **Update the "Versions and support" table in the README** — add the new series as active and
   move the previous one down to deprecated. This is not optional:
   `tests/test_documentation_examples.py` compares the active series against `pyproject.toml`
   and fails if they disagree. That test exists because 6.0.0 shipped with 5.x still marked
   active.
2. **Check `REMOVED_IN` in `hexcore/_deprecation.py`.** It has to point at a **future** major.
   `tests/test_deprecations.py` fails if it is left in the past, so either you remove what you
   promised to remove, or you move the constant — but you cannot publish with an expired
   promise. 6.0.0 was published promising a removal "in 6.0" that did not happen; that test is
   what stops it from happening again.

⚠️ A `feat!:` in a documentation PR triggers a major. That is literally what produced 6.0.0.
